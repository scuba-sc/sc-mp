## Contract
CLI modes now use the shared receipt-aware fixture (`receipt_fixture.h`), not the legacy counter-only path. The original **16** regression scenarios remain test-only, including the integration worker's deterministic authenticated DATA replay rejection. Solo uses two local receipt admissions, listen one local and one SDK remote admission, dedicated two SDK remote admissions; all remain synthetic compositions in the same in-memory 3-Core fixture, not distinct real process/socket topologies. `rejected` demonstrates permanent invalid refusal; `sc-world` fails closed. CLI retries are capped at four attempts. `Old` means unknown prior outcome and cannot overwrite or freeze a later definitive result. Noncanonical 64-bit delta/status/value fields are rejected before narrowing.

Key is `(coordinated session authority incarnation, authenticated SDK peer ID, monotonically increasing command ID)`. Process-local epochs allocate monotonically, refuse exhaustion; SDK peer IDs never reused within a session. No payload-supplied sender identity. Epoch is shared directly by fixture, not a negotiated world/session protocol. No persistent or process-restart uniqueness claim.

`SendResult::Ok` means queued by SDK, never applied. Authority `Queued` means admitted but no mutation yet. Only `Applied` is an applied outcome. `Invalid` is permanent validation rejection, retained idempotently. `Stale`, `Disconnected` and invalid IDs refuse mutation. Reusing an ID with another delta gives `Conflict`, a variant-specific diagnostic, not an outcome for the original command; client accumulator must not let it replace/poison the original result. Clients must never intentionally reuse IDs with differing payloads.

Authority ingress16, peer/tombstone slots16, last terminal receipts8 per peer, client observations32, wire datagram2048, medium256 datagrams /262144 payload bytes across ALL endpoints/directions including duplication/injection. Authority `step()` is the synthetic application execution tick; not owner-drain. No application receipt outbox grows: immediate SDK send either succeeds or increments failure count. Caller retries same immutable command to recover receipt; no automatic retry scheduler. Reliable queue stays SDK bounded. Result broadcast is SDK from-host channel; peers filter addressed peer ID, not confidentiality.

IDs must be consecutive per peer. `Gap` and ingress `Overload` are retryable no-admission outcomes and do not advance highwater. Once admitted, ID advances highwater and is never admitted again even after receipt eviction. Retries within last8 terminal results recover identical outcome/value; older IDs return `Old`, an explicit permanent refusal with **unknown prior outcome**, NOT a claim it never applied. At-most-once mutation remains within incarnation after eviction. Exactly-one mutation is established only for admitted valid commands that reach the execution tick, with recoverable outcome inside the bounded retention window; no unqualified end-to-end exactly-once/durable guarantee. Queued duplicates do not consume another slot. Disconnect revokes pending commands and retains terminal rejection/highwater. Peer tombstones never reclaim: after16 distinct peers a new incarnation is required; peer-cap Overload is no admission but not guaranteed to resolve automatically. No wraparound.

## Follow-up scope and concurrency

The receipt authority now allocates process-local incarnations atomically and cannot be copied or moved with a duplicate incarnation. The counter is local to one linked copy of this fixture, not coordinated across processes or independently loaded copies. Its other methods and state remain single-threaded: callers must serialize admission, execution, and disconnect. A known disconnected peer retains its earlier receipts and high-water mark but cannot admit new IDs. The fixture still relies on the SDK to reject messages from peers after they leave; a disconnect for a peer with no previously admitted command does not allocate a tombstone. The synthetic integration checks a captured, previously undelivered command after that disconnect as well as revocation of an admitted command. These changes do not establish durable identity, entity ownership, real process topologies, or game authority.
